# Config keys the loader parses that NO enforcement code reads.
#
# Generated and checked by test_inert_key_sweep.sh. Each line is a config path
# whose leaf identifier appears only in: the struct declaration
# (include/naab/governance.h), the loader (src/runtime/governance_config.cpp),
# and/or the config generator (src/cli/governance_init.cpp).
#
# THIS IS A SCREENING SET, NOT A LIST OF DEFECTS. Read that literally.
#
# The scan excludes the loader from the consumer search, which produces FALSE
# POSITIVES whenever the loader is itself a legitimate consumer -- when it copies
# a key into a subsystem's config struct rather than merely parsing it. Six
# entries here are exactly that and ARE live: the telemetry forwarding keys
# (forward_batch_size, forward_buffer_max, forward_retry_count,
# forward_timeout_ms, forward_shutdown_drain_ms, webhook_auth_header) are read at
# governance_config.cpp and handed to TelemetryForwarder, which uses them under
# shorter names (batch_size, buffer_max, ...). They are kept in the baseline
# because this file's job is CHANGE DETECTION, and removing known false positives
# would make the set drift from what the scan computes.
#
# The opposite correction is also live: tightening the rule to count any loader
# read as consumption drops the set from 77 to 2, because ratchet comparisons and
# `extends` merging read every key they guard. Neither heuristic is trustworthy
# alone.
#
# So: NEVER act on an entry here without verifying that key empirically --
# configure it at a value that must trip, run a program that must trip it, and
# include a POSITIVE CONTROL proving enforcement was live in that same run.
# Verified this way so far: limits.code.max_functions / max_variables /
# max_total_polyglot_lines, limits.execution.total_executions and
# limits.memory.total_mb / per_block_mb are genuinely unenforced (six set to 1, a
# 40-line two-block program exits 0 with "0 violations", while languages.blocked
# blocks the identical program at exit 3).
#
# WHY THIS FILE EXISTS
#
# Three inert-or-inverted mechanisms have been found in this engine, and all
# three were found BY ACCIDENT from an unrelated direction, never by review:
#   * CONTRA-007 iterated a set its own loader empties at parse time.
#   * The circuit breaker's middle levels were gated on a threshold belonging to
#     a different feature, so ELEVATED and HIGH were unreachable through pressure.
#   * code_quality.<check>: {"enabled": false} silently turned the check ON.
# A key that is parsed, clamped, ratcheted and inherited looks alive from every
# angle except the one that matters. This baseline turns "found by accident" into
# "fails in CI".
#
# HOW TO CHANGE IT
#
# Adding a line is a claim that a new config key enforces nothing. Do not add one
# to make the suite green -- wire the key up, or delete it. Removing a line is
# the good direction: it means a key that used to enforce nothing now does.
#
# AN UNREAD KEY DOES NOT MEAN AN ABSENT FEATURE
#
# This distinction was got wrong once already, in the alarming direction, and the
# four categories below are all present in this file:
#
#   A. No enforcement exists. The limit is simply not implemented. VERIFIED
#      EMPIRICALLY for limits.code.max_total_polyglot_lines / max_functions /
#      max_variables, limits.execution.total_executions and limits.memory.total_mb
#      / per_block_mb: all six set to 1, a program with 40+ polyglot lines across
#      two blocks runs to completion, exit 0, "0 violations" -- with
#      languages.blocked as a positive control on the identical program and
#      harness, which does block at exit 3. These are the real gaps.
#
#   B. The feature is LIVE and the toggle is inert. trust_policy.check_revocation
#      and trust_policy.check_key_expiry are the case: TrustStore::loadTrustedKeys
#      skips revoked and expired keys UNCONDITIONALLY, and trust_store.cpp never
#      consults the governance config at all. Setting either key to false does not
#      disable anything. Wiring these up could therefore only permit WEAKENING --
#      the opposite of the "unprotected" reading their names invite.
#
#   C. A live check whose sub-option is ignored.
#      requirements.error_handling.require_try_catch / require_catch_body are read
#      nowhere, while the check itself runs off a different field
#      (rules().require_error_handling). The rule enforces; its two knobs do not.
#
#   D. Feature absent and the default admits it.
#      trust_policy.require_fresh_signature defaults to false and no
#      signature-age comparison exists anywhere, so nothing is promised.
#
# `meta.*` and `meta.inheritance.*` are a fifth, benign case: the loader itself is
# their legitimate consumer, since they configure parsing.
#
# So triage before acting. The keys worth wiring or deleting are category A.
