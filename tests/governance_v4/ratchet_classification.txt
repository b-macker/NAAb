# How the mid-run reload ratchet treats govern.json keys it does not NAME.
#
# Read by tools/ratchet_coverage.py and pinned by test_ratchet_coverage.sh.
# A key the ratchet names in a string literal (its violation/notice text)
# is credited automatically; this file covers the rest:
#
#   <key>  ratchet "<token>"   compared, under a message that does not spell
#                              the key out; <token> MUST appear in a string
#                              literal of the ratchet code, or the entry is
#                              reported "hollow"
#   <key>  inert    -- why     parsed, and nothing consults it
#   <key>  startup  -- why     read once before the program runs; a reload
#                              cannot change its effect
#   <key>  neutral  -- why     changes no enforcement in either direction
#
# Every other key the loader reads is UNCLASSIFIED and listed in
# ratchet_unclassified_baseline.txt -- the debt, which may only shrink. Moving
# a key from there to here is a claim: an inert/startup/neutral line needs a
# reason that says how it was established (traced, or observed), and a ratchet
# line needs a reload test, because "named" proves the ratchet MENTIONS a key,
# not that it compares it in the right direction.

# --- Bundle 8 PR 2: the keys the unclassified baseline listed ----------------
# Every key below was in ratchet_unclassified_baseline.txt (773 keys at
# 2026-10-31); the baseline is now empty. Two new classes are ENFORCED by the
# engine, not just recorded: tools/ratchet_coverage.py --emit-orders compiles
# every `order` and `fixed` line into src/runtime/ratchet_declared_orders.inc,
# and evaluateReload() refuses a reload that moves one the loosening way
# (checkDeclaredOrderRatchet, governance_config.cpp):
#
#   <key>  order K [default=J] -- why
#          K: true / false (that value is the tighter), lower / higher (the
#          smaller / larger number is tighter), lower0 (as lower, but 0 means
#          unlimited and is the loosest), level (hard > approval_required >
#          soft > detect > advisory), enum:a<b<c (loosest first), superset
#          (removing an entry loosens), subset (adding one loosens).
#          J: the value an absent key has. With no default, adding or
#          removing the key mid-run is refused.
#   <key>  fixed -- why   no single tighter direction: ANY mid-run change refused
#
# The comparison reads the raw JSON at the key's path in the installed file and
# the new one. A section present on one side only is refused (its presence can
# itself be the on switch), so is a section that changed form (shorthand <->
# object), and an entry naming an ancestor covers every key below it. Reasons
# say how each was established: traced (the consumer was read), struct (a
# governance.h comment), rule (a pattern checked on the section's consumer) or
# untraced (fixed, fail closed -- the owner's decision for unclear keys,
# 2026-10-31). Probe: test_declared_order_ratchet.sh.
